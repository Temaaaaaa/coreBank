# CoreBank Lite

CoreBank Lite is an educational banking REST API intended to demonstrate clear,
production-style backend development suitable for a Junior Java developer portfolio.

The current version supports customers, bank accounts, deposits, withdrawals, transfers,
and paginated transaction history. Account status changes have not been implemented yet.

## Technology stack

- Java 21
- Maven and Maven Wrapper
- Spring Boot 3.5
- Spring Web and Spring Data JPA
- PostgreSQL 17
- Flyway
- JUnit 5, Mockito, and Testcontainers
- Springdoc OpenAPI
- Docker Compose

## Requirements

- Java 21
- Docker Desktop

## Local PostgreSQL

The Compose configuration uses safe development defaults. To customize them, copy
`.env.example` to `.env`; the real `.env` file is ignored by Git.

```shell
docker compose up -d
docker compose ps
docker compose down
```

To remove PostgreSQL together with local database data:

```shell
docker compose down -v
```

## Run the application

Start PostgreSQL first, then configure the application connection and run Spring Boot.
Example for Windows PowerShell when PostgreSQL is exposed on port 15432:

```powershell
$env:DB_URL='jdbc:postgresql://localhost:15432/corebank'
$env:DB_USERNAME='corebank'
$env:DB_PASSWORD='corebank_dev'
.\mvnw.cmd spring-boot:run
```

The application uses `DB_URL`, `DB_USERNAME`, and `DB_PASSWORD`. If `DB_URL` is not
specified, its local default uses `POSTGRES_PORT`, or port 5432 when that variable is
also absent.

## Customer API

Create a customer:

```http
POST /api/v1/customers
Content-Type: application/json

{
  "firstName": "Artem",
  "lastName": "Ivanov",
  "email": "artem@example.com"
}
```

Successful response: `201 Created`, with a `Location` header.

```json
{
  "id": "c4f540b1-194d-4be7-bb96-64df4b06334c",
  "firstName": "Artem",
  "lastName": "Ivanov",
  "email": "artem@example.com",
  "createdAt": "2026-07-11T18:00:00Z",
  "updatedAt": "2026-07-11T18:00:00Z"
}
```

Retrieve a customer:

```http
GET /api/v1/customers/{customerId}
```

## Account API

Open an account for an existing customer:

```http
POST /api/v1/customers/{customerId}/accounts
Content-Type: application/json

{
  "currency": "RUB"
}
```

Successful response: `201 Created`, with `Location: /api/v1/accounts/{accountId}`.

```json
{
  "id": "22222222-2222-2222-2222-222222222222",
  "accountNumber": "12345678901234567890",
  "customerId": "11111111-1111-1111-1111-111111111111",
  "currency": "RUB",
  "balance": 0.00,
  "status": "ACTIVE",
  "createdAt": "2026-07-11T18:00:00Z",
  "updatedAt": "2026-07-11T18:00:00Z"
}
```

Retrieve one account or all accounts of a customer:

```http
GET /api/v1/accounts/{accountId}
GET /api/v1/customers/{customerId}/accounts
```

Account numbers are generated by the server as 20 digits. A new account always has
balance `0.00` and status `ACTIVE`. Supported currencies are `RUB`, `USD`, and `EUR`.
The customer account list is not paginated in this first version.

Deposit money into an active account:

```http
POST /api/v1/accounts/{accountId}/deposits
Content-Type: application/json

{
  "amount": 1500.25,
  "description": "Initial deposit"
}
```

Successful response: `201 Created`, with
`Location: /api/v1/transactions/{transactionId}`. The response describes the successful
deposit transaction.

Deposit amounts must be positive and have at most two decimal places; values are never
silently rounded. Deposits are allowed only for `ACTIVE` accounts, and the transaction currency
is always taken from the account. Updating the account balance and recording the transaction
are one atomic database transaction. The account row is locked for writing during the operation,
so concurrent deposits cannot overwrite each other. Every successful deposit creates exactly one
`DEPOSIT` record; failed operations leave both the balance and transaction history unchanged.

Withdraw money from an active account:

```http
POST /api/v1/accounts/{accountId}/withdrawals
Content-Type: application/json

{
  "amount": 500.00,
  "description": "ATM withdrawal"
}
```

Successful response: `201 Created`, with
`Location: /api/v1/transactions/{transactionId}`. The amount must be positive, contain no more
than two fractional digits, and cannot exceed the current balance. An inactive account or
insufficient funds produces `409 Conflict`; insufficient-funds responses do not expose the
current balance. Balance reduction and the `WITHDRAWAL` transaction are committed atomically.
The same PostgreSQL pessimistic row lock used by deposits prevents concurrent withdrawals from
creating a negative balance.

Transfer money between two active accounts of the same currency:

```http
POST /api/v1/transfers
Content-Type: application/json

{
  "sourceAccountId": "11111111-1111-1111-1111-111111111111",
  "targetAccountId": "22222222-2222-2222-2222-222222222222",
  "amount": 500.00,
  "description": "Transfer between accounts"
}
```

Successful response: `201 Created`, with
`Location: /api/v1/transactions/{transactionId}`. Source and target accounts must be different,
active, and use the same currency. Both account rows are locked in stable UUID order to avoid
deadlocks. Both balance changes and the single `TRANSFER` record are committed atomically.
Currency conversion is not implemented.

Retrieve one successful transaction:

```http
GET /api/v1/transactions/{transactionId}
```

Successful response: `200 OK`. If the transaction does not exist, the API returns `404 Not Found`
with error code `TRANSACTION_NOT_FOUND`.

Retrieve the transaction history of an account:

```http
GET /api/v1/accounts/{accountId}/transactions?type=TRANSFER&from=2026-08-01T00:00:00Z&to=2026-08-31T23:59:59Z&page=0&size=20&sort=createdAt,desc
```

The response contains `content`, `page`, `size`, `totalElements`, and `totalPages`. Transactions
are included when the account is either their source or target. The optional `type` filter accepts
`DEPOSIT`, `WITHDRAWAL`, or `TRANSFER`; `from` and `to` are inclusive ISO-8601 instants.

Pagination defaults to `page=0` and `size=20`; `size` must be between 1 and 100. Sorting defaults
to `createdAt DESC` and supports only `sort=createdAt,asc` or `sort=createdAt,desc`. Transaction ID
is always used as a secondary sort key in the same direction to keep page ordering stable. Unknown
query parameters and invalid filter, pagination, or sorting values return `400 Bad Request`.

## Tests

Windows:

```powershell
.\mvnw.cmd test
```

Unix-like systems:

```shell
./mvnw test
```

Integration tests start an isolated PostgreSQL Testcontainer and do not use the
Compose database.
